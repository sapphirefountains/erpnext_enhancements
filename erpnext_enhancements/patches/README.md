# `patches/` — One-time migration scripts

These are Frappe **patches**: scripts that run **once** during `bench migrate` and are recorded so they never run again. They are ordered in [`../patches.txt`](../patches.txt), which splits them into two phases:

- **`pre_model_sync`** — runs *before* DocType schema changes are applied (use for renames that must happen before the new JSON syncs).
- **`post_model_sync`** — runs *after* schema changes (the default; use for data backfills and Custom Field/Property Setter creation).

Each patch's module docstring describes what it migrates. This README is the index.

| Patch | Phase | What it migrates |

| `rename_plaid_settings_doctype` | **pre** | Renames this app's Single "Plaid Settings" → **"Plaid Banking Settings"** and gives ERPNext its own "Plaid Settings" back. ERPNext v16 ships a Single of that exact name (module ERPNext Integrations) behind its native Plaid Link + transactions sync. Two DocTypes with one name cannot coexist: `sync_all` imports a DocType JSON whenever its `migration_hash` differs from the stored one (`modified` is only consulted for non-DocType records), so both apps re-imported every migrate and the later-installed app — ours (v1.148.0) — overwrote the native `tabDocType` record with our field list while `tabSingles` kept the native rows; erpnext's code read `plaid_env` off a schema that no longer declared it and our widget read `plaid_enabled` off a row that never had it. `frappe.rename_doc(..., force=True)` moves **every** `tabSingles` row to the new name (`DocType.after_rename`, and it skips the file rename while `in_patch`) and, via `rename_dynamic_links`, re-points erpnext's own "Plaid Settings" card on the Invoicing workspace and item on the Banking sidebar at the new name — which `sync_all` never repairs, because a workspace whose DB stamp is not older than its JSON is skipped. So the patch then `UPDATE`s those navigation rows back (Workspace Link / Sidebar Item / Shortcut / Desktop Icon; this app ships none that reference the name), moves every `tabSingles` row that is not one of **our** fields back — the six native values and the Single's meta rows (`name`, `modified`, `owner` …), so "Plaid Banking Settings" is left with no rows and loads with its declared defaults — resets the `name` row's value, moves/deletes the relevant `__Auth` rows (our retired `plaid_access_token` is deleted under either name — a bearer token must not outlive its field), and `reload_doc("erpnext_integrations", "doctype", "plaid_settings", force=True)` so the native record exists again before `sync_all`. **Bumping a `modified` cannot "fix" a name clash** — the hash decides and app order breaks the tie; only distinct names do. Idempotent from the DB state: absent / already native / already renamed all no-op. |

Deliberately redundant with the `before_migrate` hook `setup/module_map.py`, which does the same on **every** migrate; this is the one-shot inside the same `@atomic` phase as `sync_all()`. |
| `delete_chat_module` | post | Removes the retired chat module's database residue ([ADR 0011](../../decisions/adr/0011-retire-google-chat-and-coworker-chat.md), v1.426.0). ## Important note from `patches.txt`

The legacy `delete_master_project` and `rename_master_projects` patches from the original standalone `project_enhancements` app are **intentionally not carried over**. Master Project is now a first-class, actively-used doctype (shipped DocType + the Project link field `custom_master_project` + Project Dashboard logic). Those one-time patches already ran on legacy sites; re-running them here under the new module path would delete the active doctype/field and break new installs.
