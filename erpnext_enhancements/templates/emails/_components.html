{# The email component macros. Every piece of styled markup this app emails lives here, exactly once. Nothing else in the app may contain an email hex colour or an email ; docs/email-design-system.md is the guide. Since v1.494.0 the palette is the Sapphire Fountains design system's own tokens, applied as the "Pillar Stripe" concept: the body is ink-700 Lato on white, labels and links are bahama-blue, the display face carries every heading, the primary button is the sapphire fill with a navy-900 label (the off-white label the website uses reads 2.8:1 and is the one pairing the design system itself flags), and rules do the separating — no tinted cards, no shadows, square structure. The chrome around the body, including the pillar stripe, is _shell.html's. TWO RULES, both load-bearing: 1. **This file may not reference `frappe`.** No get_url, no _(), no escape_html. Translated strings and absolute URLs arrive as arguments. That buys three things: `{% import %}` works without `with context`; the bench-free test renders this file under a vanilla jinja2 Environment with no frappe stub at all; and a macro has no route to site state. 2. **frappe's Jinja env has NO autoescape.** Every macro therefore `|e`s its own text arguments, so a caller may hand it raw user input. URLs are emitted UNESCAPED on purpose — entity-escaping a get_url() breaks the link — so callers must pass a URL they trust; email_style.button() runs them through utils.url_safety first. Styling is inline and already correct at 320px. The @media block in _shell.html only improves it; nothing here may depend on that block. The display face is named first in DISPLAY but will almost never arrive: frappe inlines every email through premailer, whose _parse_style_rules keeps @media rules and drops every other at-rule — @font-face included (verified against premailer 3.10). {# The call to action. Table-wrapped rather than a bare padded  so Outlook
   renders the fill; bgcolor AND background so Outlook and the rest agree.

   The design system's primary button: sapphire fill, radius-10, a bold label
   in capitals — type the capitals into the label, the style adds none — and a
   navy-900 label rather than the website's off-white one, which reads 2.8:1.

   `width:auto` on the table and `padding:0;border:0` on the cell are NOT
   redundant defaults — they are overrides, and without them the whole coloured
   pill is not the link.

   The body cell carries `class="ee-pad ee-md"`, and the shell declares
   `.ee-md table{width:100%}` and `.ee-md td{border-bottom:1px solid …;padding:9px 10px}`
   so that md_to_html()'s attribute-less tags get styled at all. Premailer inlines
   those descendant rules onto EVERY table and td in the body, this one included.
   The cell then stretched the full measure while the  stayed the width of its
   own text, so the coloured bar was 772x60 and the link inside it 212x41 — 19% of
   what looks like the button. Clicking the colour did nothing (v1.331.2).

   So every macro here that draws a td must declare `padding` AND `border`, and
   every table its `width`, or it silently inherits the markdown body's. Measured
   in a browser against the premailer output of a real sent message: 100% of the
   pill is the anchor, 0 dead pixels on any edge.

   The padding stays on the , never on the td: the anchor's own box is what the
   client makes clickable. `mso-padding-alt` hands Outlook's Word engine the same
   padding, since it ignores inline-block — the fill is then the right size there,
   though only the text is the hit target. A  with 
   would fix that too, at the cost of a hard-coded pixel width per label. #}
{% macro button(url, label, tone="primary") -%}
{%- set t = TONES.get(tone) or TONES["primary"] %}


	

		{{ label|e }}
	



{%- endmacro %}
