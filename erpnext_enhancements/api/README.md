# `api/` — Whitelisted HTTP endpoints

This package holds the app's Frappe **whitelisted endpoints** (`@frappe.whitelist()` functions reachable over HTTP), plus a handful of doc-event hooks, background workers, and scheduler jobs that live alongside them. Endpoints are called from the app's desk client scripts (`public/js/...`), the standalone Time Kiosk PWA, desk Pages, and external server-to-server webhooks (Twilio / the "Triton" telephony gateway).

Every function is documented inline. This README is the map.

  - `telephony.append_call_transcript` / `get_call_transcript` / `get_caller_info` / `update_caller_info` / `process_unified_recording` / `process_unified_sms` and `call_intelligence.process_call_intelligence` — guarded by `@validate_webhook_secret`, which despite its name checks no shared secret: the caller must send a Frappe API key (`Authorization: token key:secret`, what Triton sends), which Frappe verifies before the handler runs, and the request must no longer be Guest. Any enabled API key passes, not only Triton's. Its old `Bearer <admin_webhook_secret>` branch was removed in 1.502.2: Frappe v16 401s an unrecognized Bearer before any handler runs, and the branch compared against the masked `****` placeholder rather than the decrypted secret, so it could never have matched.
  - `telephony.receive_mms` — guarded by `@validate_twilio_request` (HMAC signature).
  - `telephony.get_telephony_routing` — guarded by `@validate_webhook_secret`. Since 1.403.0 its
    `routing` block carries staff **mobile numbers**, resolved from Employee records so the
    gateway needs no lookup of its own. That makes the shared secret on this endpoint load-bearing
    in a way it was not when the payload was two softphone identities: treat a widened response
    here as a disclosure decision, not a plumbing one, and never move it to `get_gateway_config`,
    which is unauthenticated by design.
- **Session-trust:** `time_kiosk` derives the Employee from `frappe.session.user` and rejects a mismatched claimed employee (`_resolve_employee`). `log_geolocation_batch` also refuses, whole, a batch queued under another person's kiosk offline marker (`offline_key`, reason `other_person`; `workforce/kiosk_offline.py`), so a shared phone never files one person's unsent positions as another's. The legacy single-point `log_geolocation` still trusts the supplied `employee` for back-compat. `travel.py` uses the same model: `get_my_trips`/`get_itinerary_bootstrap` derive the employee from the session; `get_trip_itinerary`/`get_trip_views`/`preview_itinerary_email`/`get_trip_map_data` gate via `frappe.has_permission`, which the Travel Trip permission hooks scope to owner/crew/coordinators; anyone past that gate may see any crew member's itinerary (`as_employee` must be on the crew; anyone else is refused with one plain sentence and is never looked up, and the argument is annotated `str` so a filter dict never reaches `frappe.db.get_value`), but money on the trip views is built only for a coordinator, on the server (see [`travel_management/README.md`](../travel_management/README.md#trip-views-and-the-money-rule)); `send_itinerary_email` lets non-coordinators send only to themselves. The Trip Sheet's `ee_trip_sheet` re-checks read or print on the trip itself, because a Jinja global is reachable from any template on the site, on the trip as saved (loaded again by name: `printview.get_html_and_style` renders a document posted as JSON, whose owner, crew and job the caller writes, and the permission hook passes one with no `creation`), and compares `&as=` against the crew rather than looking it up.
- **Owner-gated, no role bypass:** `training.py` — every attempt-scoped endpoint loads the Training Attempt and refuses unless `attempt.user == frappe.session.user` by hard equality. A Training Manager gets no bypass here on purpose (they use the desk, where the DocPerms and `training/permissions.py` decide); `ignore_permissions=True` is used only *after* that assertion. Learner, employee and customer are always derived from the session — a payload key named `user` or `employee` is dropped. Catalogue visibility is computed in `_visible_course_names` and the content reads that follow are unchecked by design, since learner roles hold no DocPerm on the Training content doctypes at all.
- **Owner-or-reviewer, by hard equality:** `feedback.py` — a request is readable by a `System Manager` or by the person whose `requested_by` equals `frappe.session.user`, and by nobody else. The two intake endpoints are `submit_request` (any signed-in user, for themselves) and `submit_capture` (System Users only, `_require_system_user()`); every other mutating endpoint calls `_require_reviewer()`, i.e. `frappe.only_for("System Manager")` in effect. The DocPerms are the backstop (`System Manager` full, `All` read `if_owner`), and the *absence* of a write grant to the owner is load-bearing rather than an oversight — see the file map row.
- **POST-only:** every one of `training.py`'s thirteen whitelisted endpoints declares `methods=["POST"]` (v1.299.4), and all eleven of `feedback.py`'s do for the same reason — a GET puts the request id and the reviewer's decision in the access log, the browser history and the next `Referer`. `tests/test_feedback_endpoint_surface.py` asserts the decorator, that every name in the SPA's `M` map resolves, and that no endpoint is left both un-wired and un-explained. Not CSRF theatre — these carry the attempt id, the lesson key and the checkpoint timestamp, and a GET writes all three into the web server's access log, the browser's history and the `Referer` header of whatever the learner clicks next. The client had always posted and `www/training.html` had always said so in a comment; the server simply never enforced it. `tests/test_training_endpoint_surface.py` asserts the decorator on every endpoint, and separately that every name in the player's `METHOD` map resolves to a real one — a rename with no matching edit there is a 404 the learner sees.
- **A role gate, then the framework's own permissions:** `stock_scan.py` admits `stock_scan_rules.SCAN_ROLES` (System Manager, Stock Manager, Stock User, Inventory Clerk) and then inserts, submits and cancels every Stock Entry and Purchase Receipt as the session user **without** `ignore_permissions` — so User Permissions on Warehouse or Project still apply, and a clerk without Stock User gets a clear refusal at the voucher rather than a page that will not open. Only the `Stock Scan Log` row, the page's own record, is written with `ignore_permissions`. Undo is owner-within-the-window or a Stock Manager (`undo_refusal`) — for a store-run line, owner-within-the-window or Purchase/Accounts Manager, and never once reviewed; a `client_ref` that belongs to another user's save is refused, not returned. All thirteen endpoints are `methods=["POST"]`.
- **Write-permission-gated answer keys:** `training_author.get_builder_bootstrap` is the only call in the Training module that hands `is_correct` (and `correct_text_answers`) to a browser. It gates on `frappe.has_permission("Training Course", "write", doc=course)` on top of `_require_author()` — that gate is the entire difference between an author editing an answer key and a learner reading one, so it must not be relaxed to `read`. The learner side never serves an answer key at all (`training.py`, `training/grading.py`).
- **Role-gated:** `time_kiosk.close_interval_for_employee` -- closing your *own* session needs no role, but naming another employee requires `TIMELINE_MANAGER_ROLES` and is recorded against the requester (`closed_requested_by`). There is deliberately no on-behalf clock-*in* anywhere: a supervisor's phone is not the crew member's, and opening a job is exactly what the geofence exists to prove. `time_kiosk.add_manual_interval` / `update_interval_times` — your own intervals need no role; writing time for **another** employee needs `workforce.approval.APPROVER_ROLES`, via `_assert_may_edit_time_for`. Deliberately not `TIMELINE_MANAGER_ROLES`: that set is pinned to the Location Timeline page's roles, so reusing it would mean letting a supervisor fix a timesheet also hands them everyone's GPS trail — and it is the narrower set, predating the Operations Manager and Production Manager roles the supervisors actually hold. `time_kiosk.get_location_history` / `export_location_history` / `refresh_tracking_health` — only `TIMELINE_MANAGER_ROLES` (`System Manager` / `HR Manager` / `Projects Manager`) may view *another* employee's history; everyone else sees only their own. `get_live_positions` and the full employee picker are manager-only outright. The `get_my_*` views and the correction-request endpoints always resolve the employee from the session. `integrations_health.get_health` / `run_drive_test` — `System Manager` only (`frappe.only_for`), and they return integration secrets only as `configured: true/false`, never the values.
- **Service-role-gated, read-only:** `knowledge_base_mirror.snapshot` admits only the **KB Mirror** role (seeded with `desk_access = 0` and no DocPerm anywhere, so an account holding only it is a Website User, with no Desk, and nothing to read through `/api/resource`, a list or a report) or Administrator, and refuses every other session before it reads. **A role with no DocPerm does not keep an account out of whitelisted methods**: v16's whitelist refuses only a Guest, so a signed-in Website User reaches every login-only endpoint in this package, and in the app, whose body checks nothing (when this was written, `sync_contact.get_contacts_for_context` returned any party's contact phone numbers and email addresses, and `link_existing_record` / `unlink_record` wrote Contact and Address links under `ignore_permissions`; v1.561.1 gave those their own permission checks, and the guard remains for the next such endpoint). So the mirror's account is confined in code as well: `knowledge_base/mirror_guard.confine_mirror_account`, an `auth_hooks` entry (v16 reads the API key after `before_request`, so it has to be one), refuses a Website User holding KB Mirror every request except `GET` of the snapshot's exact path with no `cmd`, before Frappe dispatches it. Past that check it reads with `frappe.get_all`, because the role has no DocPerm to read with; what it returns is the published knowledge base, which every staff user already reads. GET only, and rate limited (counted before the role check, so a refused call counts too). Its own code reads no request header, the `Authorization` header included, which Frappe has read and dropped before it runs: the account and its key are managed outside this repo.
- **Per-assignment people, checked in the endpoint:** `my_work.py`'s actions read the ToDo and test the session user against its own people (`_abilities`), because v16's ToDo permission query is not applied to a whitelisted call: only the assignee completes or reschedules (as `assign_to.close` insists); the assignee or whoever assigned it reassigns; only whoever assigned it nudges or withdraws; a System Manager may reschedule, reassign and withdraw anything. The **Unclaimed** view reads ToDos the viewer otherwise could not (Triton files call follow-ups with no assignee and no record, owned by triton@): one with no record is shown to every System User, one on a record only to those who may read it. The triage endpoints are System Manager only. Since Phase 3 the leads in `LEAD_ROLES` (System Manager, President, Executive Team, Operations Manager, Production Manager) get the System Manager's reschedule / reassign / take-back and alone see `get_team_board`; a team queue item (a ToDo whose `role` is a "… Team" Role, no assignee) is visible to and claimable by that Role's holders and the leads.
- **Owner-gated:** `comments.update_comment` / `delete_comment` allow edits/deletes only when `comment.owner == frappe.session.user`.
- **Write-permission-gated broadcasts:** `collab.broadcast_field_update` / `broadcast_focus` require **write** permission on the specific document, enforce the settings-driven doctype allowlist (`get_collab_doctypes()` — master switch + child table on ERPNext Enhancements Settings) plus field validation and a value-size cap, and only re-publish to the doc's realtime room (whose membership Frappe's socket.io already permission-checks) — they never persist anything.
- **Project-gated reads (purchasing is *not* separately permission-checked):** `pickup_routing.get_pickup_route_data` gates on `Project.check_permission("read")` and then reads Purchase Orders / Suppliers / Addresses with `frappe.get_all` — i.e. `ignore_permissions=True`. Anyone who can open the job therefore sees its vendors, PO totals and lines regardless of their Purchase Order permissions. Deliberate: it matches the Procurement Tracker on the same Budget tab (`project_enhancements.get_procurement_documents`, whitelisted with **no** gate), and this endpoint is the tighter of the two. Hiding purchasing from some Project readers would mean moving both to `frappe.get_list` together. That call also returns the **Travel Settings Google Maps browser key** to anyone past the gate: a referrer-restricted browser key reaches the client either way (same reasoning as `travel.get_trip_map_data`), and its only real protection is the HTTP-referrer restriction set in the Google Cloud console.
- **`pickup_routing.get_supplier_pick_data` gates on `Purchase Order` read instead, and that is the whole gate.** Deliberately stricter than its project-scoped sibling above, for a structural reason rather than a stylistic one: that endpoint is *anchored* to a Project the caller can already open and shows only that job's spend, whereas this one is anchored to nothing. Without a doctype-level check it would hand any authenticated user every open order, every job and every total for a vendor of their choosing. Every read past the check is `frappe.get_all` (ignore-permissions), so removing it removes all of it — replace it with `frappe.get_list` or not at all.
- **Permission-checked reads:** `activity_log`, `comments` read endpoints, and `search` re-check `frappe.has_permission` / filter with `ignore_permissions=False` before returning data. `gantt.get_gantt_data` treats its whole config as hostile input: `frappe.has_permission` gates the call, rows come from `frappe.get_list` (never `get_all`), every fieldname in the field map / filters / order_by must exist on `frappe.get_meta(doctype)` (start/end restricted to Date/Datetime fieldtypes; uncoercible date values skip the row instead of raising), limits clamp at 1000, and dependency links are dropped unless **both** ends are rows the permission-checked query returned. Composite mode applies the same rules per doctype: the child doctype gets its own `has_permission` gate and validated `get_list`, and child rows are constrained to roots the root query returned. **Writes** (`update_gantt_row`) reuse the same validators: the target doctype must be one the config already addresses, only `start`/`end`/`progress` may change and only via the validated field map, `has_permission(..., doc=name)` is checked per document, submitted docs are refused, and the row is written with `doc.save()` (never `db.set_value`) so validation, doc events and realtime all fire.
- **Role-gated preview:** `telephony.preview_call_routing` is `frappe.only_for("System Manager")`. It answers who would ring for a hypothetical call, which means it discloses the same staff mobile numbers and the shape of the on-call arrangement — so it is gated to the role that can already edit the rules. It also resolves the caller with `create_if_missing=False`, because a *preview* that quietly creates a Customer and Contact for every number somebody types would be its own bug.
- **Role-gated, value zeroed rather than refused:** `activity_cost.get_activity_cost` replaces ERPNext's endpoint of the same name, which returned any employee's Activity Cost `costing_rate` (a burdened pay rate since v1.480.0) to any logged-in caller. A caller holding none of `PAY_AUDIENCE_ROLES` gets `costing_rate: 0`; one holding a role still needs `frappe.has_permission("Employee", "read", doc=employee)`, so User Permissions apply. It zeroes instead of raising because the Timesheet form's prefills feed the value straight into arithmetic, and a 0 is what `update_cost` treats as unset, so the save fills the real rate in server-side. The permlevel-1 Property Setter on `Activity Cost.costing_rate` is enforced where frappe reads a document out (the form, list views, `GET /api/resource`), never on a whitelisted function's own read, which is why this override exists. Frappe does not enforce it on the document a write call sends back either (`frappe.client.save`, `PUT /api/resource`, and so on), so a Projects User who saves an Activity Cost would get `costing_rate` back; `fieldlevel_read.py` scrubs those responses (v1.542.0).

## Gotchas

- `gemini.py` authenticates with an OAuth2 token minted from the Drive service account (`Project Folder Google Drive Settings`), which must hold `roles/aiplatform.user` on the hard-coded GCP project (`sapphire-fountains-poseidon`); `Triton Settings.maps_api_key` is no longer read. The model is a constant (`gemini-3.8-flash`) on the **global** endpoint — 3.1 Pro is served *only* there, and the regional host answered 404 with a message that reads like a missing IAM grant. Google retires the recent Flash models 45 days after a replacement ships, so revisit `MODEL_ID` when a Flash lands; a retired id is a 404 on every call, every caller falls back, and the Integrations Health tile reports the last narrative's source.
- `telephony.get_softphone_token` hard-codes the Twilio identity `"nikolas_erpnext"`.
- `telephony.get_caller_info` has a **write side effect** — it auto-creates a Customer + Contact for unknown numbers and commits, despite reading like a lookup.
- `analytics.py` requires the service-account JSON to be a **Private** file (`/private/files/...`); a public path is rejected to avoid leaking the key. Its docstrings mention raising `ValidationError`, but the code actually returns `{"error": ...}` dicts.
- `maintenance_workflow.check_warranty_and_rma` raises native **Warranty Claims** (one per failed in-warranty water feature); the old Material Request + `"WARRANTY-RETURN-PENDING"` placeholder flow is gone.
- Approving a maintenance visit issues **no** stock (v1.594.0). The visit records each chemical's dose in the unit the technician counts in, and stock moves by the container on the Stock Scan page. The old `create_stock_entry` step was removed.
- `workspace_utils.get_workspaces_for_user` returns only **public** workspaces.
- `maintenance_scheduling.update_next_visit_dates` runs once per maintenance submit, from the `on_submit` doc-event in `hooks.py` (the historical duplicate controller call was removed).
- `training_author.save_draft_version` **reports** every field it did not apply, in the response's `rejected` list, instead of dropping it quietly. Autosave that answers "saved" while losing the author's paragraph is worse than a save that fails, and the loss is only discovered on reload. Adding a field to the builder UI therefore means adding it to the matching `*_ALLOWED_FIELDS` set; forgetting surfaces as a warning on the first autosave. Fields the bootstrap emits that are server-owned mirrors (`lesson_key`, `block_key`, `video_duration_seconds`, …) are listed in the `*_ECHOED_KEYS` sets and skipped in silence, because echoing them back is not lost work.
- `save_draft_version`'s `modified` optimistic lock is **mandatory**, unlike `maintenance_visit.save_visit`'s (which tolerates `None`): a caller with no token never loaded the draft. The token is the *version's* `modified` and stands in for the whole builder document — the version is saved unconditionally on every call so the token still advances on a payload that only touched lessons, which are separate documents.
- `save_draft_version` saves the version **before** the lessons. `TrainingLesson._validate_chapter` reads the version's chapter keys from the database, so a lesson moved into a chapter created in the same payload would otherwise be rejected.
- `save_draft_version` manages quiz **pool membership only** (`question`, `points`, `is_required`). A Training Question is a shared, reusable document that can sit in another course's pool, so body fields arriving in a quiz row are refused and reported rather than applied. Question wording is edited on the Training Question form or via `training_ai.accept_ai_suggestions`; checkpoints likewise are not written by autosave.
- `reorder_lessons` writes with `db.set_value(..., update_modified=False)` on purpose: position is not content, and a drag must not be able to fail on an unrelated half-finished block elsewhere in the course. `_draft` has already refused a published version, which is the guard `db.set_value` bypasses.
