# `tests/` — Test suite

Tests for the app's server-side behavior. Most extend Frappe's `FrappeTestCase` and therefore need a **real bench** to run; several suites are deliberately bench-free. Note that `bench run-tests` is BROKEN under Python 3.14 — bench-backed suites expose a module-level `run()` wrapper invoked with `bench execute` instead (see `test_contacts_ux.py` and `test_fountain_move_conversion.py`).

## Running

```bash
# Bench-backed tests (most of this folder):
bench --site <site> run-tests --app erpnext_enhancements

# Bench-free suites (plain pytest/unittest, no site required):
python -m pytest erpnext_enhancements/tests/test_quickbooks_online.py
python -m pytest erpnext_enhancements/tests/test_assistant_tools_schema.py
python -m pytest test_sync_time_kiosk.py        # at repo root
```

> CI currently runs only the standalone `unit-tests` job; the Frappe integration-test job was removed in v0.2.9 (see [`CHANGELOG.md`](../../CHANGELOG.md)) because it gated PRs on upstream/environment churn. The `FrappeTestCase` files remain and run against a real bench locally.
>
> Within that job, the unittest-style suites run via `python -m unittest` with an explicit module list, and `test_quickbooks_online.py` runs via a dedicated `python -m pytest` step — it is plain pytest functions (the `monkeypatch` fixture), which unittest cannot collect. A new bench-free suite must be added to one of those two steps in [`ci.yml`](../../.github/workflows/ci.yml) (pytest-style → the pytest step), or it will never run in CI.

**The 56 `test_chat_*.py` suites went with the chat module** ([ADR 0011](../../decisions/adr/0011-retire-google-chat-and-coworker-chat.md), v1.426.0), together with the 58 CI steps that ran them and the `chat/README.md` section that explained what each one defended. `test_chat_module_retirement.py` in the table above is what replaced the lot. Two rules they taught outlive them, because neither was ever about chat:

- **A bench-free suite that stubs `frappe` at module scope needs its own CI step.** Every chat suite had one for exactly this reason: run together in one process they go red for reasons that have nothing to do with the code under test. `test_po_pdf_filename.py` carries the same warning above, and it is why several bench-free suites are listed separately in [`ci.yml`](../../.github/workflows/ci.yml) rather than appended to a module list.
- **A build gate is not a coverage suite, and a gate asserting *absence* must read comment-stripped source.** `test_chat_rawsql_guard.py` was the first shape — an `ast` walk that failed the build on a raw query missing its permission filter, where the fix was always to satisfy the rule rather than add an exemption. The retirement sweep is the second, and it needs the stripping: the comments explaining what was removed necessarily name it.

The three browser modules the Triton widget kept from that client are guarded by plain-`node` scripts rather than by anything in this folder: `scripts/test_triton_markdown.mjs` and `scripts/test_triton_citations.mjs` (both renamed from `test_chat_*` when the modules moved to `public/js/triton/`), `scripts/test_triton_widget_guards.js` (which is what covers `keys.js`, by asserting the widget imports `isComposingKey` rather than re-implementing it), and `scripts/fuzz_url_safety.mjs` piped into `scripts/fuzz_url_safety_check.py`.
